Abstract

Answering clinical questions over Fast Healthcare Interoperability Resources (FHIR) records requires assembling evidence that is scattered across reference-linked resources and buried in deeply nested attributes. Existing agents give these raw resources to a single model, which must retrieve, relate, and compute within one long context. We present FHIR-GRAMS, a multi-agent framework that first normalizes the FHIR graph into canonical clinical views and then divides the reasoning: a planner routes the query to resource-specific specialists that select the relevant fields, and a composer answers from the aggregated evidence with retrieved skills and deterministic tools. On four FHIR question-answering benchmarks, FHIR-GRAMS improves accuracy over the strongest baseline by 11.6 and 8.0 points with two Gemini backbones, while using fewer tokens and less time per query.

Approach

A patient's FHIR record is a graph of typed, nested JSON resources linked by references. A single clinical event is often split across resources: a prescription may carry no drug name and only point to a separate Medication resource, while the dispense record spells the same drug differently. FHIR-GRAMS separates evidence processing from answer composition.

Hierarchical FHIR graph normalization

Every resource is flattened into path–value pairs, and a hand-written map assigns each path a canonical field name. Resources that belong to one clinical entity are then merged into a single canonical view: a medication request, the Medication it references, and its dispenses and administrations become one flat medication view. Every entry keeps the resource it came from, so the agents read compact, consistently named fields while each value stays traceable to the record. Views are computed once per patient and form a layer above the original resource graph.

Planner

Reads only the question and selects the view types it involves, guided by a routing skill, so the decision does not grow with the size of the record.

Specialists

One agent per view type keeps only the canonical fields the question needs; metadata and raw codes are hidden by a fixed exclude list.

Composer

Retrieves the top-K procedure skills (temporal reasoning, code matching, cross-resource integration) and plans chains of 13 deterministic atomic tools in a plan-and-execute loop for up to N rounds.

Efficiency

FHIR-GRAMS needs about 12 s and 26k tokens per query with either backbone, less than multi-turn CodeAct (15–18 s, 28k–42k tokens) and GRASP (12–20 s, 46k–57k tokens), because the specialists bound the evidence that reaches the composer. Among reported systems, FHIR-Hopper uses a similar number of tokens (21k–23k) but is less accurate on FHIR-AgentBench (56.8–61.1 vs. 65.5–66.7 judged).

Ablations

On FHIR-AgentBench with Gemini-2.5-Flash, adding the planner and then the specialists to a composer that reads the full normalized record raises judged accuracy by 8.8 points at almost half the tokens (57.9 → 66.7, 51.8k → 28.3k). Replacing raw resources with canonical views alone improves accuracy from 48.1 / 56.4 to 52.3 / 61.1 while lowering tokens. In skills, success and failure indicators help, whereas worked examples hurt and cost about 3.8k more tokens.

What's Next: FHIR-R1

FHIR-GRAMS reaches its accuracy with hand-written skills and frozen API models. In ongoing work, FHIR-R1, we move from agent design to agent training: a multi-turn tool-using Qwen3-8B agent over patient FHIR records is post-trained with reinforcement learning (DAPO). A teacher that receives privileged information is trained first and then distilled into a deployable student, which sees only the question and the record, through on-policy self-distillation.
